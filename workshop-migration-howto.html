워크샵 Azure-Samples 이관·표준화 가이드

개인 리포에서 운영하던 워크샵을 Azure-Samples 조직으로 옮기면서 팀 표준 템플릿을 함께 적용하는 방법을 안내합니다. 반복 변환 작업은 AI 에이전트에 맡기고, 저자는 결정과 리뷰만 하면 됩니다.

기준일 2026-09-16 · 근거: 표준화 제안과 상세 규격 부록 A~D · 표준을 적용한 실물 예시: AzureAIFoundryWorkshop-Code@standard-v2

개요 · 문서 구성

이 페이지에서 전체 흐름을 확인한 뒤, 아래 상세 가이드·결정 시트·AI 지시문으로 작업을 진행합니다. 표준 규칙은 Markdown 기준 문서에서 검토·개정하며, 아직 결정되지 않은 항목은 구분해 표시합니다.

사람이 읽는 문서

상세 이관 가이드

전체 절차(Phase 0~6)와 단계별 판단 기준. 유형별 차이는 부록에 정리되어 있습니다.

저자가 채우는 문서

이관 결정 시트

이관 범위, 콘텐츠 유형, history 방침, 라이선스, 제외할 내부 산출물을 기록하는 양식입니다.

AI에 전달하는 문서

AI 변환 지시문

Copilot Agent와 Claude Code에서 사용하는 변환 지시문. 결정 시트 값을 입력 블록에 채워 전달합니다.

이관 절차 (Phase 0~6)

절차는 일곱 단계입니다. 변환과 검증을 전부 로컬에서 끝낸 뒤 마지막에 Azure-Samples로 게시하므로, 표준화가 끝나지 않은 콘텐츠가 공개 조직에 올라가는 일이 없습니다. 저자가 직접 하는 일은 결정 확정, 보안 판정, 변경 리뷰, 게시와 실행 검증이고 나머지는 AI가 수행합니다.

1
Phase 0 — 사전 결정 (선택). DECISION-SHEET를 채우는 단계지만 건너뛰어도 됩니다. 건너뛰면 다음 단계의 시트 인터뷰에서 에이전트의 권고안으로 결정합니다.
2
Phase 1 — AI 실행과 결정 확정. 구 리포를 클론하고 지시문을 에이전트에 전달합니다. 시트가 없으면 에이전트가 리포를 분석해 전 항목 권고안(권고값 + 근거)을 한 번에 제시하고, 저자는 확인·수정으로 확정합니다.
3
Phase 2 — 보안 점검. 커밋 이력 전체를 대상으로 시크릿, 개인 리소스 식별자, 노트북 출력을 스캔합니다. 생략할 수 없는 필수 게이트입니다.
4
Phase 3 — 콘텐츠 이관 준비 (로컬). 이력 보존, 스쿼시, 서브폴더 추출 중 결정대로 로컬에서 새 리포의 뼈대를 만듭니다. 원격 push는 아직 하지 않습니다.
5
Phase 4 — 표준 적용. AI가 경로 표준화, 식별자 placeholder 치환, frontmatter, 랩 구조와 골격, 노트북 정리, devcontainer, AGENTS.md, 거버넌스 파일(LICENSE 2종·SECURITY·CODE_OF_CONDUCT·SUPPORT)까지 별도 브랜치에 단계별 커밋으로 수행합니다.
6
Phase 5 — 검증과 리뷰. 하네스 9종 통과 로그를 확인하고, 변경 요약 보고와 로컬 diff를 리뷰한 뒤 TODO를 채웁니다.
7
Phase 6 — 게시와 등재. Microsoft Open Source Management 포털에서 <product>-<topic>-workshop-kr 리포를 저자가 직접 만들고(Private, Non-Production, Direct Owner 개인 2명, 오픈소스 심사 Yes), Ruleset protect-main을 Disabled로 임포트한 뒤 push하고 Active로 전환합니다. Codespaces에서 완주하는 E2E 검증 후 validated_on을 기입하고, 심사 승인 뒤 Publicize로 공개 전환합니다. 허브 리포 카탈로그에 등재하고 구 리포는 리다이렉트 README로 바꿔 Archive 처리합니다.
필수 규칙 보안 점검에서 시크릿이나 개인 식별자가 커밋 이력에서 발견되면, 저자 선택과 무관하게 history는 스쿼시로 강제됩니다. HEAD에서 지워도 이력에는 남기 때문입니다.

빠른 시작 — AI로 변환하기

실제 작업 흐름은 다음과 같습니다. 준비물은 구 리포와 AI 코딩 에이전트(Claude Code 또는 GitHub Copilot 에이전트 모드) 하나입니다.

1
리포를 클론하고 도구를 준비합니다. 본인 GitHub 리포를 로컬에 클론합니다. 하네스 실행에 gitleaks 8.19 이상과 Python 3.10 이상이 필요한데, devcontainer에서 작업하면 환경 문제를 피할 수 있습니다.
2
지시문을 에이전트에 전달합니다. AI 지시문을 작업 폴더에 복사하고 "이 파일을 읽고 그대로 수행하라"고 지시합니다. 결정 시트를 미리 채웠다면 [입력] 블록에 값을 옮겨두면 질문 없이 진행되고, 없으면 에이전트가 리포를 분석해 전 항목 권고안을 제시하므로 확인·수정만 하면 됩니다.
3
에이전트가 로컬에서 변환을 수행합니다. 보안 점검, 이관 준비, 표준 적용, 하네스 9종 통과까지 별도 브랜치에 단계별 커밋으로 진행합니다. 삭제 대상이나 history 방침 같은 판단 지점에서는 멈추고 확인을 요청하며, 원격 push는 하지 않습니다.
4
변경을 리뷰합니다. 변경 요약 보고에서 단계별 커밋 내역과 하네스 통과 로그를 확인하고, 저자가 채울 TODO(소요 시간, 정리 절차 등)를 채웁니다.
5
Azure-Samples에 게시합니다. 포털에서 리포를 만들고(이름 규약·오너 2명·심사 문안은 가이드 6-1) SSO 승인·JIT 승격을 마친 뒤, 이력 보존이면 표준화 브랜치를 새 리포 main으로 지정 push, 스쿼시·추출이면 일반 push로 올리고 Ruleset을 임포트해 Active로 전환합니다.
6
실행 검증 후 마무리합니다. Codespaces에서 워크샵을 처음부터 끝까지 완주하고 validated_on을 기입합니다. 심사 승인 뒤 Publicize로 공개 전환하고, 허브 리포 카탈로그에 등재한 다음 구 리포를 리다이렉트 README로 바꿔 Archive 처리하면 끝입니다.
팁 AI가 변환 중 시크릿이나 개인 식별자 노출을 발견하면 스스로 지우지 않고 멈춰서 보고하도록 지시문에 정의되어 있습니다. 이력 처리 판단과 원격 push는 항상 사람 몫입니다.

핵심 규칙

변환 과정에서 자주 판단이 필요한 지점입니다. 규격은 표준 문서, 적용 절차와 예외 조건은 상세 이관 가이드를 확인합니다.

history

보존/스쿼시는 저자 선택

기본은 리포별 저자 선택입니다. 단, 보안 점검에서 이력 노출이 확인되면 스쿼시가 강제됩니다.

노트북

출력 제거는 전 유형 공통

outputs와 execution_count 제거는 유형과 무관하게 모든 ipynb에 적용합니다. md 안내서를 페어링하는 규칙만 B·C형에 해당합니다.

경로

랩 폴더는 NN-kebab-name 하나

lab이나 step 같은 단어 접두어 없이 번호 접두어만 씁니다. 최상위에 실행 코드(src, tests)가 있으면 랩들을 labs/ 아래로 모으고, 없으면 루트에 직배치합니다 — 컨테이너명은 labs/로 통일합니다. 개명 결과를 고정하려면 path_map에 매핑을 적어두면 AI가 그대로 따릅니다.

날짜

last_updated와 validated_on은 다른 값

last_updated는 문서 수정일이고 validated_on은 사람이 완주한 날입니다. 최신성(stale) 판정은 validated_on 기준이므로 문서만 고치고 검증일을 채우지 않으면 오래된 자료로 표시됩니다.

본문

AI는 창작하지 않습니다

실습 절차의 내용을 만들거나 지우지 않습니다. 학습 목표·검증 기준처럼 원문에 근거가 있는 항목만 원문 문장을 재배치·요약해 채우고, 근거가 없는 항목은 TODO로 남깁니다.

자산

공용일 때만 shared-assets

이미지·데이터는 해당 랩의 assets/에 둡니다. 다른 랩이 참조하는 파일만 /shared-assets/로 옮기고 참조 링크를 함께 고칩니다. 같은 파일을 여러 랩에 복사하지 않습니다.

검증 하네스

변환 완료의 기준은 하네스 9종 전체 통과입니다. AI가 PR 전에 스스로 실행하므로 저자는 통과 로그를 확인하면 되고, 병합 후 유지보수 단계에서도 같은 검사를 씁니다. 검사 명령 전체는 AI 지시문과 각 워크샵 리포의 AGENTS.md에 들어 있습니다.

  • 보안 — 시크릿 스캔(커밋 이력 포함) · 개인 리소스 식별자 잔존 · 노트북 출력과 execution_count 잔존
  • 구조 — 공백·비ASCII 경로 · 루트 README의 전체 frontmatter 스키마 · 랩 README의 축약 frontmatter
  • 콘텐츠 — 깨진 상대 링크와 이미지 참조 · 빈 alt-text · 랩 전용 자산을 다른 랩이 참조하는 경우
참고 하네스는 devcontainer(Bash) 기준입니다. Windows 로컬에서는 gitleaks 설치 같은 준비 작업만 PowerShell로 하고, 검사는 devcontainer나 Git Bash에서 실행합니다.

참고 — 콘텐츠 유형 · 자료

결정 시트의 유형 판정에 쓰는 세 가지 분류입니다. 파일이 무엇이 있느냐가 아니라 수강자가 주로 무엇을 따라가며 배우는가로 판정합니다. 포털 실습에 보조 노트북이 몇 개 있어도 주 학습 경로가 포털이면 A형입니다.

유형 A

포털 클릭스루형

브라우저에서 포털을 따라가며 배우는 워크샵. Fabric처럼 SaaS 포털이 본질인 제품에 맞습니다. devcontainer 없이 execution: [portal]로 선언하고, 스크린샷 관리가 주된 유지보수 포인트입니다.

유형 B

노트북 실행형

노트북(ipynb)이 설명과 실행을 겸하는 워크샵. SDK·코드 실습에 맞습니다. 각 장에 md 안내서를 페어링하고, 출력을 지운 상태로만 커밋합니다.

유형 C

가이드 + 검증 분리형

md 가이드가 본문이고 노트북은 동작 검증에만 쓰는 워크샵. 인프라·정책 실습처럼 산출물이 코드 밖에 있는 주제에 맞습니다. 문서와 실행물의 역할이 나뉘어 유지보수가 쉽습니다.
